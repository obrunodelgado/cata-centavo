# Internal transfers never count as income or spending

Internal transfers — money moving between accounts of the same holder — never enter the income, expense, category or savings-rate figures, anywhere. This extends the exclusion `aggregate` already applied to Pluggy's "Same person transfer" (`04xxxx`) and credit-card payment (`05100000`) leaves to the whole Investments group (`03xxxx`): applying to and redeeming from your own portfolio moves money that never left the holder, so it is not spending and not income. The one exception is `03060000` (proceeds, interest and dividends), which is income.

The decision is unconditional: there is no "Conta única" toggle. The prototype's switch was considered and rejected — the raw view (internal transfers counted) produced a negative savings rate for a wallet that invests heavily (R$ 100k of applications counted as expenses in six months, −17.8% savings rate), and a toggle would have to plumb a preference through the API, the store and the UI for a number nobody wants to see. A document-based detector (counterparty CPF/CNPJ matching the holder's own document) was also considered and parked: it is redundant while Pluggy enrichment is alive (the taxonomy caught every internal transfer in the audit wallet) and only earns its keep when `category`/`categoryId` stop arriving on the free tier — see `docs/research/2026-07-26-phase-0-5-recon.md`.

Consequences: the category breakdown (donut, MCP period tools) and the period totals can never disagree, because `aggregate` excludes internal transfers from both the groups and the totals; `bucketSeries` and the bill derivation inherit the rule through the shared `isSelfTransfer`. Detection is by taxonomy leaf, deliberately not by description — bank wording for the same movement varies between institutions. A future manual "mark as internal" override would extend the resolved-category check rather than add a parallel rule.
